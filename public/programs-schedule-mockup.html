Mockup notes — what it takes to make this real

What the data already gives us

  • Card 17298 (calendar) is already session grain: date, day, begin, end, program, section, location, price, status.
  • Card 17295 (programs) already carries instructor, instructor_count, location, location_count, enrolled, utilized, capacity and registration_mode — but at section grain, so it has no per-date row to hang them on.

The three columns nothing emits yet

  • Site. session.location_id is either a court (site) id or a location id. 17298 already joins court site — and uses it only to resolve the location, throwing the site name away. One column.
  • Instructor per session. The path is section_facilitator → instructor → users via instructor.user_id; the obvious users.id join matches 0 rows and, being a LEFT JOIN, would render an empty column rather than erroring.
  • Confirmed count per session — the real work. See the two decisions.

Two decisions before anyone writes SQL

  • Which unit the count is in. A per-session section has real per-meeting seats; a per-section one only has a run total. Printing both as a bare “18/24” makes them look comparable when they are not — hence the grain chip and the legend.
  • Whether a per-section run repeats. Shown here on every date it meets, which is what “a listed view by date” means. The alternative is one row per section on its start date, which is a different report.

The roster link: the UUID already exists

  • The programs side is already done. Card 17295 emits section_id (s.id AS section_id) today, programs.html already maps it (sectionId: raw['Section Id']), and it already drives the section-detail drill-down. Card 17298 carries it too, inside Section URL. Nothing to add — the new session-grain card just carries it onto each session row.
  • The destination needs no work either. Card 17296 already filters on org_id, start_date, end_date, section_name, is already session grain, and roster.html already reads all four off the URL and auto-runs.
  • The one gap is that the roster cannot RECEIVE an id. Of card 17296's 22 output columns not one is an id (Rec ID is the participant's 6-character desk code), and it has no section_id template tag — so today the only key on offer is section_name, an ILIKE '%name%' with no program filter.
  • Which is why the name alone will not do. Measured over a live 37-day window: 3,160 of 21,944 section-dates (14.4%) would open a roster carrying other sections' participants — 432 spanning two or more programs, across 41 orgs, worst case 31 sections collapsed onto one link. Platform-wide, 14,833 of 24,739 live sections share their name exactly with another section in the same org.
  • So: one push to 17296, two additive changes. The clause [[ AND section.id = {{section_id}}::uuid ]], and section.id AS "Section ID" as an output column — same push, same date-tag flip, and the column makes the join checkable from the roster's own rows. Plus three lines in roster.html to read and forward section_id. The name still rides along, only so the roster's filter chip reads legibly.
  • Filter it server-side, not in the browser. Emitting the id and cross-referencing client-side sounds equivalent and is not: apex's roster over a month is ~12,000 rows / 382 pages, so that pulls the whole window to throw nearly all of it away. The [[ ]] clause is what keeps the payload one section wide.
  • Section id plus date is exact for 98.7% of meetings. The rest are sections that meet twice in one day: 290 of 21,945 section-dates (1.3%), 14 orgs, worst case 10 sessions — there the link returns both of that day's meetings. Same enrolled people for a per-section run; genuinely different for a per-session drop-in. A Session ID on both cards closes it, and is worth doing only if one of those 14 orgs asks.

Choices worth arguing with

  • A blank instructor stays blank. 155 of El Segundo's 286 live sections have nobody on file, holding 83% of enrolments — no nudge, no “unassigned”, per the earlier call. So the instructor filter needs its own No instructor on file option, or ticking any name silently drops half the schedule.
  • Cancelled sessions stay on the page, struck through. Someone reading a wall schedule needs to know the room is free.
  • Location is the group, site is the column — identical to the rental schedule, so the two reports print the same shape.
  • A run's dates ride in the program cell in amber, where the rental schedule puts its multi-day callout.
  • No clipboard where there is nobody to list. Absent, not greyed — the same rule as the rental schedule's Forms column, which renders nothing where no form was ever requested. A link to an empty roster is the dead end this is meant to remove.
  • The roster link is scoped to the single date, so it answers "who is in this session". For a per-section run that is the same names on every date; for a per-session camp it is that day's list, which is the one worth printing.
